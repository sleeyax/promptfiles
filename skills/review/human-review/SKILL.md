# Human-driven MR review

MR: $ARGUMENTS

The **user** writes the review. This skill is a scribe and a courier: it opens the diff a concept group at a time, captures the user's editor selection plus their typed comment as an anchored finding, and posts the batch as GitLab **draft** notes at the end. It is the counterpart to `review-mr`, which generates findings itself — same payload format and same posting helper, different code path.

**Requires Claude Code in VS Code.** The editor selection (`ide_selection`) is the only anchor source and the `code` CLI is the display, so unlike the other review skills this one has no Codex or bare-terminal fallback. Stop if either is missing.

## Hard rules

- **The agent does not invent findings.** Every body is the user's words. Do not add, reword, or improve one unless asked; fixing an obvious typo is fine.
- Never publish draft notes — they stay unpublished for the user to publish or discard.
- Never push, commit, or modify the working tree.
- Every gate is a real stop: ask with `AskUserQuestion`, then wait for the answer. Never assume one.
- Posting is gated by exactly one confirm covering the whole batch, and `post-draft-note.sh` runs **exactly once**. No per-comment shell calls — rollback on partial failure is the helper's job.
- **Never print diff text to chat.** The editor is the display; chat carries headers, prompts, and at most the two or three lines a comment anchors to.
- Notes post with a `<!-- human-review -->` marker so a later run can recognise them. The helper appends it — never write it into a body or strip it from one.
- Proactive commentary is off unless the user turns it on (`suggest on`).

## Workflow

### 1. Preconditions

Check all of these first. Stop with a clear message on any failure.

1. `glab`, `jq`, `awk`, and `code` on PATH; `glab auth status --hostname <host>` healthy.
2. cwd is the MR's repo (`git remote -v` matches).
3. Resolve the MR — from `$ARGUMENTS`, else `glab mr list --source-branch "$(git branch --show-current)"`. If none or several, ask.
4. Resolve the numeric project id once (`glab api "projects/<urlencoded-path>"` → `.id`); some GitLab versions reject URL-encoded paths on `/draft_notes`.
5. Fetch `diff_refs` (`base_sha`, `start_sha`, `head_sha`). Bail if null, or if `state` is `merged`/`closed`.
6. **Assert `git rev-parse HEAD` == `head_sha` and `git status --porcelain` is empty.** This is what makes the user's editor line numbers identical to GitLab's `new_line`. If HEAD differs, offer `glab mr checkout <iid>`. If the tree is dirty, stop — do not stash silently.

### 2. Load the MR's conversation

```
./existing-threads.sh --project <id> --mr <iid>
```

Returns published discussions and unpublished drafts keyed by path under `.files`, plus `humanPaths`, `lastHuman` and `counts` — the notes the **user** wrote, told apart from `review-mr`'s by the marker and by its "Generated by AI" footer. Two uses: surfacing the existing conversation per group (step 5), and resuming (step 3). Never re-add a draft that is already there.

### 3. Resume where the user left off

Check for `<scratchpad>/human-review-<iid>.plan.json`, then ask for state — with a plan file now, without one after step 4:

```
./review-state.sh --plan <plan.json> --findings <findings.json> --threads <threads.json>
```

Drop `--findings` when nothing is queued locally. `humanPaths` still maps onto a freshly built plan, so a lost scratch directory costs the plan, not the progress.

Report `totals.comments` queued locally, `totals.remoteComments` already on the MR, `furthest`, and `lastHuman` as `path:line · <first line>`. Then ask:

- **Continue at group `<continueAt.index>`: `<title>`** (recommended) — after the furthest group commented on, where the walk stopped
- **Back to group `<resumeAt.index>`: `<title>`** — only when `skippedGroups` is non-empty
- **Start over, keep queued comments** — re-plan, keep the findings file
- **Discard and start fresh** — delete plan and findings, after saying the comment count out loud. The only destructive option here, and it leaves the MR untouched.

Skip the prompt when `furthest` is null and nothing is queued.

If `diffRefs.headSha` in the findings file no longer matches the MR's `head_sha`, the branch was pushed to and **every queued anchor may have moved**: offer only *Discard* or *Post what is queued now*. Drafts already on the MR anchor to their own session's `head_sha`; say how many are affected and leave them to the user.

Then create `<scratchpad>/human-review-<iid>.json` with `diffRefs` and `findings: []`, unless one is being kept.

### 4. Plan the walk

Do this **before** opening any file — 70 files in alphabetical order buries the decisions that matter.

1. `./analyze-diff.sh --base <base_sha> --head <head_sha>` returns per-file status, `+/−`, the subjects of the commits that touched it, and up to 6 hunk-header contexts. Signal only — do not read file diffs to build the plan. Files where `oldPath != path` were moved: keep the pair in one group, say so, and pass them to `open-diff.sh` through a paths-file as `path<TAB>oldPath`.
2. Group by **concept**, not directory. Commit subjects are the strongest signal — they are already the author's own grouping. A file touched by several commits belongs to its dominant change.
3. Order groups by review value, hardest-to-reverse first:

   | Order | Group kind | Why first |
   |---|---|---|
   | 1 | Schema, migrations, entities | Costly to change once shipped |
   | 2 | API contract, DTOs, public types | Breaks consumers |
   | 3 | Core business logic | Where the bugs are |
   | 4 | Wiring — controllers, DI, config | Mechanical, but easy to misroute |
   | 5 | Consumers — frontend, SDK callers | Fallout from 1–3 |
   | 6 | Tests | Read after the code they cover |
   | 7 | Generated, renames, formatting | Skim or skip |

   Within a group order entry point → detail, deletions last. That order is load-bearing: it is the order the tabs open in, and the order closing them walks.

4. **Cap a group at ~10 files** — every file opens as a tab at once. Split anything larger along the seam that reads most naturally, usually layer, and title the parts so the split is obvious (`Generic storage · backend`, `· frontend`).
5. Persist to `<scratchpad>/human-review-<iid>.plan.json` as `[{title, rationale, files:[…]}]` — a separate file, because `findings.schema.json` sets `additionalProperties:false`. It outlives a posted batch; never delete it as part of posting.
6. Present for approval: group titles, file counts, `+/−`, and any existing comment count — one line each, no file lists. Ask **Start** / **Reorder** / **Drop a group** / **Flat A–Z instead**, folding in the step 3 resume choices when there is progress. Re-plan until the user starts.

### 5. Enter a group

Print, and nothing more:

- `━━ Group i/N · <title> · <n> files · +A −D`
- 2–4 sentences: what it changes, why these files belong together, what is worth scrutinising. Ground it in the signals; do not speculate about code you have not read.
- The ordered file list, one line each, with a short clause on each file's role. Mark moves as `<path>  ← moved from <oldPath>`.
- Existing conversation on these files, from step 2: `path:line · @author · <first line>`, marked `(resolved)`, `(draft)` or `(yours)`. Omit the block when there is none.

Then open the whole group at once, most important first:

```
./open-diff.sh --base <base_sha> --head <head_sha> --path <first> --path <second> …
```

Pass the paths in planned order and nothing else. The helper reads the VS Code settings that decide tab placement and post-close focus, and arranges both the tab strip and the most-recently-used stack so the group's most important file is active and closing it reveals the next — the user can walk a group with `Ctrl+W` alone. Do **not** pass `--tmp`: the base pane defaults inside the repo on purpose, which is what pins the diff to the VS Code window that owns this folder.

Opening costs one to two `code` calls per file, so a large group takes a second or two. Report anything that came back `{"opened":false}` (binary, or no diff entry) in one line.

### 6. Capture comments

The unit of navigation is the **group**, not the file: its tabs are all open, so the user moves between them by clicking, in any order, for as long as they want. Do not prompt or nudge — capture, confirm, and otherwise stay quiet.

A comment is captured when the user's message arrives with an `ide_selection`, or when they state a line number explicitly.

- `path` — the selection's file, relative to repo root. `oldPath` = `path` unless renamed.
- `lineRange` — the selection's first and last line as new-file numbers; `start == end` for one line. Omit only for a bare line number with no selection.
- `line` — the anchor, **always the range's last line**. GitLab requires this.
- Per endpoint, from the hunk headers: added (`+`) line → `{newLine}` only; context line → `{newLine, oldLine}`. Removed lines cannot be selected.
- `body` — the user's text verbatim, minus any severity prefix: `blocker:`, `concern:`, `nit:`, or none/`suggestion:` for `suggestion`. Severity sorts the pre-submission list and is not posted.

Check every anchor before queueing:

```
./check-anchor.sh --base <base_sha> --head <head_sha> --path <p> --start <N> --end <M>
```

| `verdict` | Meaning | Do |
|---|---|---|
| `ok` | selection contains lines this MR added | queue it |
| `context-only` | inside a hunk, no added lines | queue it, note once that this MR did not change the code |
| `outside-diff` | not inside any hunk | **warn first** — GitLab stores the note and never renders it. Offer `nearestHunkLine` or the summary instead. |

Then echo `✓ [n] <severity> · <path>:<start>-<end>` and **append to the scratch file immediately** — a long review outlives a context compaction.

When a comment implies a concrete replacement, offer to make it a GitLab suggestion; never convert unprompted or invent text beyond what the user said. Append to the body:

````
```suggestion:-<end−start>+0
<the whole of the selected lines, replaced>
```
````

The span is not free-form: the anchor is the last line, so a captured `start..end` must use `-(end−start)+0`. `post-draft-note.sh` aborts the batch on a mismatch rather than let Apply rewrite the wrong lines in the author's branch.

### 7. Group boundary

At the end of every group ask rather than waiting for typed input — clicking beats typing `next` sixty times. Append a live count to the question: `N comments queued · group i/N done`.

- **Next group: `<title>`** (recommended) — name it, so the choice carries information
- **Re-open this group** — tabs were closed, or the user wants another pass
- **Jump to a group…** — then list the remaining groups
- **Finish and review queue** — go to step 8

A typed comment at a boundary is a comment on the group just finished, not an answer to the prompt. Capture it and re-prompt.

### 8. Pre-submission

On `done`, or after the last group:

1. Print the coverage report from `./review-state.sh` (same call as step 3): `filesCommented` of `filesTotal`, `groupsTouched` of `groupsTotal`, and every `untouchedGroups` entry by name, splitting `totals.comments` about to post from `totals.remoteComments` already there. Twelve well-formed comments look like a finished review even when four groups were never opened; state it plainly and leave the judgement to the user.
2. Print the numbered list, grouped by file, sorted `blocker` → `nit`: `[n] <severity> · <path>:<start>-<end>` + the body's first line, summary as `[S]`, `(suggestion)` on entries carrying a fence.
3. Ask **Post all** / **Drop some** / **Edit some** / **Review an untouched group** / **Cancel**. Offer the fourth only when `untouchedGroups` is non-empty.
4. **Drop some** / **Edit some** → apply, rewrite the scratch file, back to 2. **Review an untouched group** → back into the walk at that group. **Cancel** → exit without posting and give the scratch path.

### 9. Post

Optionally verify with `--dry-run` first, which prints the payloads and posts nothing. Then, exactly once:

```
./post-draft-note.sh --project <id> --mr <iid> --findings <scratch.json> --marker '<!-- human-review -->'
```

It validates against `findings.schema.json`, skips anything matching an existing draft, verifies each note's anchor and `line_range.end` landed, and `DELETE`s the whole batch on any failure. Success prints `{"posted":N,"skipped":M,"ids":[...]}`.

On success delete the findings file and `rm -rf "$(git rev-parse --show-toplevel)/.git/human-review"`, but **keep the plan file** — posting mid-review is normal. On failure leave the scratch file and give its path.

### 10. Report

- MR title + URL, and the `<mr_url>#drafts` link
- `posted` / `skipped` counts
- The review is **unpublished** — the user publishes or discards it in the GitLab UI
- When groups are still untouched: invoking the skill on this MR again picks up after the last group commented on, whether or not the drafts were published in the meantime

Then stop.

## Commands

| Command | Effect |
|---|---|
| `next` / `n` | Finish this group, open the next |
| `back` | Re-open the previous group |
| `groups` | Re-print the plan, order, and progress |
| `group <n>` | Jump to group `n` |
| `reopen` | Re-open the current group's tabs |
| `open <path>` | Open one extra file's diff, for context outside the group |
| `list` | Show all queued comments, numbered |
| `edit <n>` | Amend a queued comment's body, path, or lines |
| `drop <n>` | Remove a queued comment |
| `summary: <text>` | Set or replace the non-positional summary note |
| `suggest on` / `suggest off` | Toggle the agent's own per-file observations (default off) |
| `done` | End the walk, go to pre-submission |
| `quit` | Abandon; nothing posted, scratch file left in place |

With `suggest on`, add an **Agent notes** block of at most 3 observations per file, clearly marked as the agent's. They are never findings until the user promotes one.

## Notes

- The right pane is the real working-tree file, not a copy — that is what makes a selection report the true path and `new_line`. Never edit it, and re-check `git status --porcelain` before posting; if the tree went dirty, stop and say the line numbers may no longer match `head_sha`.
- A deleted file opens as old-vs-empty for context. There is nothing to anchor to, so comments on it are out of scope — say so once and move on.
- Diff tabs stay open after posting. Closing them is the user's call.
